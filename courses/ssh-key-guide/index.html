Reference · Any OS, Any Server

SSH keys, done once, done right.

A locked door only works if the key is real, not a password someone can guess. This walks through generating an SSH key pair, naming it so it never gets confused with another one, connecting it to a server, and setting up a shortcut so you never type a password again. Pick your platform below, everything on the page updates to match.

PRIVATE KEY (yours, never shared) ⟶⟶⟶ PUBLIC KEY (goes on the server)
01

What you're actually creating

Running one command produces two files: a private key that never leaves your machine, and a matching public key that's safe to hand out. They're mathematically linked, anything encrypted against the public key can only be unlocked by the private one. A server that trusts your public key will let you in the moment you prove you hold the matching private half, no password ever exchanged, nothing to guess or intercept.

Rule of thumb: the file without .pub is the one you protect like a password. The file with .pub is the one you're meant to copy around freely.
02

Generate the key pair

We're using ed25519, the current recommended standard: smaller, faster, and at least as secure as the older RSA format, with no key-size decision to second-guess. Name it for its purpose right from the start, don't accept the generic default filename, that's what causes confusion later once you have more than one key.

1Open PowerShell and run
Swap homeserver for whatever this key is actually for, e.g. github, work-vps.
POWERSHELL
ssh-keygen -t ed25519 -C "your-name-homeserver" -f $env:USERPROFILE\.ssh\id_ed25519_homeserver
💡 The -f flag sets the save path and filename directly, so PowerShell won't even ask, and you'll never land on the ambiguous default name.
2Set a passphrase, or skip it
You'll be prompted to type a passphrase twice. This encrypts the private key file itself, so if your laptop is ever stolen, the key alone isn't enough to use it. Optional, but recommended for anything protecting real infrastructure. Press Enter twice to skip it if you'd rather prioritize convenience.
1Open a terminal and run
Swap homeserver for whatever this key is actually for, e.g. github, work-vps.
BASH / ZSH
ssh-keygen -t ed25519 -C "your-name-homeserver" -f ~/.ssh/id_ed25519_homeserver
💡 The -f flag sets the save path and filename directly, so the terminal won't even ask, and you'll never land on the ambiguous default name.
2Set a passphrase, or skip it
You'll be prompted to type a passphrase twice. This encrypts the private key file itself, so if your machine is ever compromised, the key alone isn't enough to use it. Optional, but recommended for anything protecting real infrastructure. Press Enter twice to skip it if you'd rather prioritize convenience.
3Lock down the file permissions
Unlike Windows, Linux/macOS SSH refuses to use a private key that other users on the system could read. This is a one-time fix if you ever see a "permissions too open" error.
BASH / ZSH
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519_homeserver
chmod 644 ~/.ssh/id_ed25519_homeserver.pub
03

Naming, so you never lose track

Every key ssh-keygen generates without a custom name is called id_ed25519. Do that twice and the second run just asks if you want to overwrite the first. Name every key for what it unlocks, not what algorithm it uses, the algorithm is already in the filename.

Avoid
id_ed25519
Fine for a single key on a single machine. The moment you add a second purpose, this becomes ambiguous and risks being silently overwritten.
Prefer
id_ed25519_homeserver
id_ed25519_github
id_ed25519_workvps
One glance at the filename tells you exactly what it's for. Scales cleanly to as many keys as you end up needing.
04

Put the public key on the server

This step tells a specific server to trust your new key. You still need password login working once to do this, it's how the server first learns your public key exists.

1Pipe the public key to the server
Replace user and server-address with your actual login and hostname or IP.
POWERSHELL
type $env:USERPROFILE\.ssh\id_ed25519_homeserver.pub | ssh user@server-address "cat >> ~/.ssh/authorized_keys"
💡 This is the last time you'll need to type that account's password, assuming the connection test in the next section succeeds.
1Use ssh-copy-id, the built-in tool for exactly this
Replace user and server-address with your actual login and hostname or IP.
BASH / ZSH
ssh-copy-id -i ~/.ssh/id_ed25519_homeserver.pub user@server-address
💡 If ssh-copy-id isn't available (rare, but happens on minimal systems), fall back to: cat ~/.ssh/id_ed25519_homeserver.pub | ssh user@server-address "cat >> ~/.ssh/authorized_keys"
05

Set up a shortcut with an SSH config file

Instead of remembering the full username, hostname, and which key goes with it every time, teach SSH the pattern once. One config file can hold entries for every server and key you ever set up.

1Open (or create) the config file
POWERSHELL
notepad $env:USERPROFILE\.ssh\config
⚠ If Notepad prompts to create the file, when you save, set Save as type to All Files. Otherwise Notepad silently appends .txt, and SSH will never find it.
1Open (or create) the config file
BASH / ZSH
nano ~/.ssh/config
2Add a Host block
Give it a short alias, this is what you'll type from now on instead of the full connection string. Add one block per server, stacked underneath each other.
~/.ssh/config
# A short, memorable alias for this connection
Host homeserver
    HostName your-server.local
    User your-username
    IdentityFile ~/.ssh/id_ed25519_homeserver

# Add more servers the same way
Host github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_github
💡 On Windows, ~ inside this file is understood the same way, no need to write out the full C:\Users\... path here.
3Connect using the alias
ANY TERMINAL
ssh homeserver
If it connects without asking for a password (a passphrase prompt for the key itself is expected if you set one), you're fully set up.

When it doesn't work

The handful of things that actually go wrong, and the fix for each.

07

Back up the private key

If you disable password login on a server (recommended, and covered in the homelab build log), losing this file and physical access to the server at the same time is the one true lockout scenario. Back it up somewhere durable before that becomes a problem instead of after.

Good
Password manager file attachment
Encrypted, synced, recoverable even if the original machine is gone entirely.
Good
Encrypted USB drive
Keep it separate from any installer USB drives you're also using.
Avoid
Plain cloud storage, no passphrase set
Anyone with access to that cloud account effectively has your server too. Fine only if the key itself has a passphrase.
Never
Email, chat, or any ticket system
These are not encrypted-at-rest by default and often get indexed or logged elsewhere.
